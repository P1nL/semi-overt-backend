# 02 服务职责与边界

## 为什么读这份文档

这份文档解决的是“改需求时先去哪个服务”和“什么事情不能在这个服务里做”的问题。重点不是列类名，而是讲清楚每个服务在系统中的业务职责，以及越界修改会带来什么后果。

## `gateway-service`

负责：

- 统一公网入口
- JWT 校验与失效处理
- 内部头注入
- 路由分发
- 基于 Redis 的网关限流

不该负责：

- 文章、用户、审核等业务真源
- 直接操作业务表
- 代替下游做业务规则判断

## `auth-service`

负责：

- 用户注册、登录、登出、找回密码
- 用户资料与公开主页基础信息
- token 签发
- 对内提供用户摘要

不该负责：

- 文章主状态
- 审核决策
- 搜索与通知结果

为什么用户真源必须放在这里：

- 否则多个服务会对同一用户事实形成分裂认知

## `content-service`

负责：

- 首页、分类、文章详情
- 文章创建、草稿、提审、取消审核、删除
- 文章主状态机
- 用户主页文章聚合
- 审核结果落地后的文章状态更新

不该负责：

- 直接维护审核任务投影
- 直接落通知结果
- 直接维护公开搜索结果

为什么文章状态真源必须放在这里：

- 因为作者能否编辑、审核是否展示、搜索是否可见、通知是否发送都要依赖这一个真源状态

## `review-service`

负责：

- 待审核任务投影
- 审核动作与审核日志
- 审核结果决定
- 最近审核原因查询

不该负责：

- 直接成为文章主状态真源
- 直接成为搜索或通知真源

## `search-service`

负责：

- `GET /api/v1/search/articles`
- Elasticsearch 搜索投影维护
- 启动时已发布文章回填索引

不该负责：

- 定义文章是否已发布
- 直接成为文章详情真源
- 绕开内容域直接修改主数据

为什么搜索不能直接当真源：

- 因为搜索本质上是检索视图，不是主状态存储

## `notification-service`

负责：

- 消费文章状态变化事件
- 生成通知主记录
- 生成投递记录

不该负责：

- 反向决定文章状态
- 承担用户真源
- 直接定义审核结果

## `file-service`

负责：

- 上传入口
- 文件校验
- 本地路径落盘
- `/static/uploads/**` 访问映射

不该负责：

- 维护文章状态
- 保存业务真源
- 决定图片属于哪个业务流程步骤

## `common`

负责：

- 内部 DTO
- 事件常量
- 请求头常量
- 公共支持类与工具类

不该负责：

- 单个服务专属的真源业务规则

改 `common` 需要格外谨慎，因为它通常会影响多个服务一起编译和一起运行。
