# 03 核心业务链路

## 为什么读这份文档

这份文档用“业务链路”而不是“文件列表”来解释系统。读完后，你应该能把一个用户动作从入口一路追到数据库、消息队列和搜索结果。

## 链路一：注册与登录

流程：

1. 请求先进入 `gateway-service`
2. 网关识别公开认证路由并允许匿名访问
3. 请求转发到 `auth-service`
4. `auth-service` 完成注册或登录
5. 登录成功后签发 JWT
6. 后续请求再进入网关时，由网关解析 JWT 并注入内部头

这条链路的意义：

- 认证真源集中在 `auth-service`
- 公网鉴权入口集中在 `gateway-service`
- 下游服务基于内部头拿用户身份，而不是重复解析公网 token

## 链路二：文章创建与草稿保存

流程：

1. 已登录用户通过网关调用 `content-service`
2. `content-service` 创建文章元数据或更新草稿
3. 草稿正文缓存进 Redis，元数据持久化进 MySQL
4. 定时任务在需要时把草稿缓存刷回数据库

这条链路的意义：

- 草稿不是简单的“每次都直接写 MySQL”
- 把正文缓存和元数据持久化拆开，是为了提升创作过程的保存体验

## 链路三：提交审核

流程：

1. 作者在 `content-service` 发起提交审核
2. 内容域校验文章状态、冷却时间、作者身份等规则
3. 文章主状态变更为 `PENDING`
4. 内容域写出 `ArticleSubmittedEvent`
5. `review-service` 消费该事件，生成审核任务投影

这条链路的意义：

- 提审不是只改一行文章状态
- 审核域需要感知这篇文章进入待审队列

## 链路四：审核通过或退回

流程：

1. 管理员通过网关调用 `review-service`
2. 审核域读取内容域提供的审核快照
3. 审核域校验权限并写审核日志
4. 审核域发布 `ReviewDecidedEvent`
5. `content-service` 消费该事件并更新文章主状态
6. 内容域继续发布 `ArticleStatusChangedEvent`

这条链路的意义：

- 审核域负责“决定”和“留痕”
- 内容域负责“真正改主状态”

## 链路五：审核结果触发通知

流程：

1. `notification-service` 监听 `ArticleStatusChangedEvent`
2. 根据状态变化生成通知主记录
3. 同时生成投递记录
4. 通知数据落 MySQL

这条链路的意义：

- 通知是派生数据
- 它的失败不应该回滚文章主状态

## 链路六：审核结果触发搜索可见

流程：

1. `search-service` 监听 `ArticleStatusChangedEvent`
2. 当状态变为 `APPROVED` 时写入或刷新 Elasticsearch 文档
3. 当状态变为非 `APPROVED` 时删除对应搜索文档
4. 搜索接口只查 Elasticsearch 投影
5. 服务启动时还会回填已有 `APPROVED` 文章索引

这条链路的意义：

- 搜索只关心对外公开可见的文章视图
- 它不直接成为文章真源

## 端到端验收主线

当前最值得拿来验证整体健康度的链路是：

`注册 -> 登录 -> 创建文章 -> 保存草稿 -> 提交审核 -> 审核通过 -> 通知落库 -> 搜索可见`

这条链路同时覆盖：

- 网关鉴权
- 用户真源
- 内容主状态
- 审核动作
- 事件总线
- 通知投影
- 搜索投影

这也是 [smoke-test.ps1](../../scripts/smoke-test.ps1) 当前校验的主线。
