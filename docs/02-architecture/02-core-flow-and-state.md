# 核心链路与状态流转

适合谁看：要理解业务主链路、状态变化和联调路径的人。  
读完能解决什么问题：知道一篇文章从创建到搜索可见经历哪些步骤，哪些状态由谁负责。

## 主链路

当前系统最重要的一条链路是：

1. 用户注册并登录
2. 作者创建文章
3. 作者保存草稿
4. 作者提交审核
5. 审核员执行审核动作
6. 内容服务应用审核结果
7. 通知服务生成通知
8. 搜索服务更新搜索可见结果

## 状态真源

文章状态以 `content-service` 为准。

这意味着：

- 审核服务维护的是审核任务与审核动作
- 搜索服务维护的是搜索可见视图
- 通知服务维护的是通知投影视图
- 真正决定文章是否已发布、是否可搜索的事实来源仍是内容服务

## 关键操作与归属

### 创建文章

- 外部入口：`POST /api/v1/articles`
- 服务：`content-service`
- 权限：登录用户

### 保存草稿

- 外部入口：`PUT /api/v1/articles/{articleId}/draft`
- 服务：`content-service`
- 权限：登录用户本人

### 提交审核

- 外部入口：`POST /api/v1/articles/{articleId}/submit`
- 服务：`content-service`
- 结果：文章进入审核链路，并触发审核任务投影

### 审核动作

- 外部入口：`POST /api/v1/reviews/{articleId}/action`
- 服务：`review-service`
- 权限：管理员
- 结果：审核决定通过事件回写到内容服务

### 搜索可见

- 外部入口：`GET /api/v1/search/articles`
- 服务：`search-service`
- 可见前提：内容服务已经完成审核结果应用，并广播文章状态变化事件

## 审核链路的责任切分

- `content-service` 负责提审和应用最终审核结果
- `review-service` 负责审核待办、动作和日志
- `notification-service` 与 `search-service` 消费状态变化，不反向成为真源

## 网关在主链路里的作用

网关并不承担业务状态判断，但承担链路入口控制：

- 判断是否允许匿名访问
- 对需要登录的接口做 JWT 校验
- 对审核接口做管理员限制
- 注入内部身份头，避免下游信任客户端自带头

## 主链路排查时的顺序

主链路异常时，建议按下面顺序排：

1. 网关是否正确返回 `401` / `403`
2. 内容服务是否成功创建或更新文章
3. 审核服务是否生成或消费审核任务
4. 内容服务是否应用审核结果
5. RabbitMQ 队列是否存在并正常消费
6. 通知和搜索投影是否已落地
